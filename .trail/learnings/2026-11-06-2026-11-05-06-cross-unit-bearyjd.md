First hardware run: `scanimage --load-film` failed at load op 24 (PollMasked mask 0xfb want 0xf0, read 0xfc for 4830 ms). 0xfc & 0xfb = 0xf8, only bit 0x08 differs (loader sensor still covered = feed did not engage). Python `of135i load` worked on the same cold unit. User pushed the magazine in one firm motion after the jog went quiet, so the "backend fires LOAD 1.1 s after the sensor edge" theory is weak. Plan: logging-only patch first (branch ot135i-v9-load-fix in sane-v9-build/A-loadfix), candidate fixes on separate branches (interrupt drain, longer settle), then one logged retest.
- Vendor recordings from Windows live in .local-research/ref/opticfilm135i-linux/traces/ (20260905-vendor-clean-load.trace.json.gz is the load reference) plus capture_empty_holder_600dpi_dev54.pcap at .local-research top level. The driver tables of135i/tables*.py are the converted form.
- Raw USB capture works from the dev container: `sudo tcpdump -i usbmon<BUS> -s 0 -w f.pcap` (bus from lsusb after each power cycle).
## Tried and ruled out
- Running load through `!` or a pipe: needs a real host terminal.
- Treating the 126 non-Qt "fixture not found" errors as real: only the system python's pytest shows them; `uv run pytest` (what CI uses) is clean.
- Launching pytest in the background without resetting SIGINT: the fake driver inherits SIG_IGN (fixed in app #112).
## Watch out
- Closing the OpticFilm app restarts the eject-watch unit if the app had stopped it: re-stop the unit before any driver session and do not open the app in between.
- An agent ran `scanimage -L` against the real scanner when told "no hardware": say "no scanimage at all" in briefs.
- Do not post anything to the upstream maintainer without the owner's go. #50 combined report is drafted (.omc/upstream-pr-drafts/issue50-v9-first-hardware-run-2026-11-05.md) and waits for the logging patch.
